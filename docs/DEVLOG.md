# 트랙 A 개발 기록

무엇을 어떤 순서로 만들었고, **왜 그렇게 정했는지**를 남깁니다.
B·C·D가 이 브랜치를 열었을 때 "이 코드는 왜 이렇게 생겼나"를 코드만 읽고 추측하지 않아도 되게 하는 게 목적입니다.

> **커밋 히스토리에 대하여**
> 이 브랜치의 커밋은 시간 순 재생이 아니라 **의존성 순서로 묶어 정리한 것**입니다.
> 계약 → 어댑터 → 렌더 부품 → 렌더러 → 입력 → HUD → 화면 → 조립 순서라, 위에서부터 읽으면
> 아래 계층을 몰라도 이해되도록 쌓여 있습니다.
> 실제로 겪은 시행착오(특히 아래 3단계의 "명세 대조 후 되돌린 것")는 이 문서에 적습니다.

---

## 1단계 — 실행되는 껍데기부터

시작 시점에 `src/` 안에 부품(계약 초안, FakeSim, 카메라, 유닛 뷰, 오브젝트 풀)은 있었지만
`package.json`도 `index.html`도 없어서 **한 줄도 실행해본 적이 없는 상태**였습니다.
부품이 실제로 맞물리는지 아무도 모르는 상태라, 제일 먼저 띄우는 것부터 했습니다.

Vite + PixiJS 8 + TypeScript(strict). 마스터 §12.1의 권장 스택 그대로입니다.

**첫 번째 판단 — 프레임 구동권은 한 곳에만 둔다**

원래 `FixedStepLoop`이 자기 `requestAnimationFrame`을 돌리고, Pixi `Application`도 자기 ticker로
rAF를 돕니다. rAF가 둘이면 실행 순서가 보장되지 않아 보간 계수 `alpha`가 한 프레임씩 밀립니다.
처음엔 어댑터의 rAF를 걷어내고 Pixi ticker가 `adapter.advance(dt)`를 부르게 고쳤습니다.

→ **3단계에서 이 결정을 되돌립니다.** 아래 참고.

## 2단계 — 조립층

부품은 있는데 이어 붙이는 층이 통째로 없었습니다.

- `GameRenderer` — 명세 §2.3의 레이어 9층을 세우고, 유닛 뷰의 수명을 관리
- `BaseView` — 본진
- `InputRouter` — 키/포인터 → Command
- `Hud` — 자원바, 유닛 버튼, 토스트

**유닛의 죽음은 한 가지 경로로만 판정합니다.** `kill` 이벤트와 "스냅샷에서 사라짐" 두 가지로
알 수 있는데, 둘 다 쓰면 사망 연출이 두 번 재생됩니다. 스냅샷 쪽만 씁니다.

**100ms 중복 차단은 공유합니다.** 명세 §5의 요구인데, 키보드와 버튼이 각자 차단 창을 가지면
"버튼 클릭 + 숫자키"가 100ms 안에 두 번 나갑니다. `CommandGate` 하나를 둘이 같이 씁니다.
프론트에서 시뮬로 나가는 출구는 여기 한 곳뿐입니다.

이 시점에 M0 DoD 4개를 전부 확인했습니다.

| DoD | 결과 |
| --- | --- |
| FakeSim 유닛 좌우 이동 및 HP 바 | 통과 |
| 카메라 자동 추적/수동 전환 | 통과 |
| 유닛 버튼 커맨드 전달 | 통과 |
| 더미 유닛 40기에서 60fps | 통과 (60fps) |

## 3단계 — 명세와 코드를 한 줄씩 대조 (중요)

돌아간다고 끝이 아니라서, 역할 명세를 조항별로 코드와 맞춰봤습니다. **위반 3건**이 나왔고
전부 되돌렸습니다. 여기가 이 브랜치에서 제일 중요한 부분입니다.

### 위반 1 — §10 "`contracts.ts`의 타입만 import한다"

`LOGICAL_MAX`, `TICK_MS`를 **값으로** 가져오고 있었습니다. 상수는 계약의 일부라고 판단해서
그냥 썼는데, 명세 문장은 "타입만"입니다.

**조치:** 두 상수를 `src/adapter/SimAdapter.ts`에 A측 사본으로 복제하고, `contracts.ts`에서는
전 파일이 `import type`만 하도록 고쳤습니다.
**남은 부채:** B가 상수를 바꾸면 A도 같이 고쳐야 합니다. 계약 회의 안건입니다.

### 위반 2 — §2.3 "HP 바는 레이어 8"

HP 바가 유닛(레이어 5)과 같은 컨테이너에 있었습니다.

**조치:** `UnitView`를 `root`(레이어 5)와 `bar`(레이어 8)로 쪼갰습니다.
덤으로 배칭도 나아졌습니다. 전에는 드로우 순서가 `유닛텍스처 → 흰색 → 흰색 → 유닛텍스처`로
번갈아 가서 텍스처가 바뀔 때마다 배치가 끊겼습니다.

> 성능 근거만 놓고 보면 40기에서 이미 60fps가 나와 이 수정은 불필요했습니다.
> 그래도 고친 이유는 **명세 조항이기 때문**입니다. 성능 판단과 명세 준수는 별개로 봤습니다.

### 위반 3 — §1 SimAdapter 인터페이스에 메서드를 늘림

명세의 인터페이스는 5개(`getSnapshot` / `send` / `start` / `stop` / `onEvents`)인데
`getInterpolation()`과 `advance()`를 더해 놨었습니다. `advance()`는 1단계에서 제가 넣은 겁니다.

**조치:** 명세의 5개로 되돌렸습니다. 그런데 이러면 §2.2의 보간을 할 수 없습니다 —
`alpha`를 계산하려면 누적 시간을 알아야 하는데 물어볼 창구가 없어집니다.

**해결:** 프론트가 **`tick` 번호가 바뀌는 순간을 직접 관찰**하게 했습니다(`Interpolator`).
`getSnapshot()` 하나만으로 동작하고, 명세 §2.2의 "직전 및 현재 스냅샷을 유지한다"와도 정확히
맞습니다. 결과적으로 1단계의 rAF 문제도 같이 사라졌습니다 — 프론트가 자기 시간만 재므로
어댑터와 렌더러의 rAF 순서에 영향받지 않습니다.

> 1단계에서 "이게 옳다"고 판단한 구조가 3단계에서 뒤집혔습니다. 명세를 먼저 정확히 읽었으면
> 한 번에 갔을 길입니다.

### 같이 걷어낸 것

DoD 측정용으로 넣었던 스트레스 스폰 모드(`?stress=40`)와 개발용 디버그 오버레이는
명세에 없는 추가물이라 제거했습니다.

### §1 인터페이스에 하나 남긴 것

`setTimeScale?()`은 optional로 남겼습니다. §3이 "T9 스폰은 0.5초 슬로우",
§6이 "gameOver 슬로우모션"을 요구하는데 §1 인터페이스에는 시간을 늦출 방법이 없습니다.
**명세 안에서 서로 어긋나는 지점**이라, 임의로 정하지 않고 optional로 두고 여기 적어 둡니다.

## 4단계 — 나머지 기능 전부

### 렌더

- `ProjectileLayer` — 시뮬은 `x`와 `progress(0~1)`만 줍니다. **포물선 Y는 프론트가 만듭니다.**
  `4p(1-p)` 곡선이라 발사점과 착탄점 높이가 같습니다.
- `EffectDirector` — §6의 이벤트 9종을 전부 연출로. 이 파일에 게임 판정은 한 줄도 없습니다.
- 카메라 연출 — T9 스폰 0.5초 슬로우 + 팬, 게임 종료 시 패배 본진 줌인.

### HUD

생산 큐(§4.2), 미니맵(§4.3), 경고(§4.4), 전략 버튼, 시대 업, 업그레이드 패널(R),
일시정지(ESC), 유닛 정보 팝업(우클릭/길게 누르기).

### 화면 흐름 (§7)

스플래시 → 메인메뉴 → 캠페인/빠른대전/도감/연구소/온라인(M3 비활성)/설정 → 인게임 → 결과.

도감은 밸런스 데이터를 그대로 렌더합니다. **이 파일에 유닛 이름도 숫자도 없습니다.**
진영·티어 필터와 이동 프리뷰까지 전부 데이터에서 나옵니다.

## 데이터가 없어서 비워 둔 곳

지어내면 "숫자는 코드에 없다"가 깨지므로, **화면에 "데이터 없음"이라고 적고** 필드가 오면
자동으로 채워지게 했습니다. 목록은 [README](../README.md#지금-막혀-있는-것--다른-트랙-대기)에 있습니다.

### (갱신) 투사체와 스킬 연출 — 이제 나옵니다

처음 이 문서를 쓸 때는 **렌더러가 완성돼 있지만 한 번도 화면에 나온 적이 없는** 상태였습니다.
`FakeSimAdapter`가 `skill` 이벤트와 `attack` 이벤트를 만들지 않았기 때문입니다.
그 결과 `UnitView.playAttack()`과 `ProjectileLayer.shoot()`이 **도달 불가 코드**였고,
화면에서는 유닛이 가만히 선 채 HP만 깎였습니다. 타입 검사로는 전혀 잡히지 않습니다.

이제 FakeSim이 공격마다 `attack`(목표 좌표 포함)을, 4회마다 `skill`을 발행합니다.
회귀를 막기 위해 [`src/adapter/combatEvents.test.ts`](../src/adapter/combatEvents.test.ts)가
이벤트가 실제로 나오는지 지킵니다.

> `snapshot.projectiles`는 여전히 빈 배열입니다. 투사체는 `attack` 이벤트로 발사되는
> 연출 전용 경로를 쓰고, 스냅샷 기반 경로는 B의 시뮬이 채우면 살아납니다.
> 두 경로가 같은 레이어를 공유하므로, 시뮬이 붙을 때 중복 표시가 되는지 확인해야 합니다.

## 검증 상태

- `tsc --noEmit` 0 에러
- `vite build` 통과
- 브라우저에서 실플레이 확인 (스폰·전투·사망 연출·카메라·HUD·본진 파괴 → 결과 화면)
- 40기 60fps

**아직 자동 테스트가 없습니다.** 렌더 코드라 단위 테스트 가치가 낮다고 보고 미뤘지만,
`Interpolator`의 `alpha` 계산과 `UnitButton`의 상태 판정은 순수 로직이라 테스트할 수 있습니다.
특히 버튼 판정은 시뮬의 거부 판정과 **순서까지 같아야** 하므로 회귀 테스트 가치가 있습니다.
